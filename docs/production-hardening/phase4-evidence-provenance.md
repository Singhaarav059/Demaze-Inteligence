# Phase 4 — Evidence Provenance System

## Scope decision

Per the Master Plan's own Section 4 instruction ("Only add these if
equivalent structures do not already exist"): this repo already has most
of the Source→Evidence→Signal→Problem→Opportunity chain built, just under
different names, spread across several 2026-07-22/2026-08-13 sessions
documented in CLAUDE.md (quote-verification via `verifyQuoteInContent`/
`isQuoteGrounded`, `claim_type: 'observed'|'inferred'` on both pain_points
and opportunities, `source: 'deterministic'|'llm_verified'|'llm_inferred'`
on opportunities, `NormalizedAnalysis.evidence: EvidenceItem[]`). Rebuilding
a parallel `Evidence`/`Signal`/`Opportunity` type system as literally
specified would have duplicated all of that. This phase instead **audited
the existing chain for a real break, found one, and fixed it** — a smaller
and more valuable diff than a rebuild.

## The real gap found

The Phase 1 benchmark run's own evaluator output was the tell:
`Evidence-backed opportunities 0/20 — 0/4 opportunities carry an
evidence_id`, repeated across nearly every one of the 10 benchmark
companies. `benchmarks/research-evaluation.ts` scores this dimension with
a plain `!!o.evidence_id` check. Traced why it was always false: every
`evidence_id` on an opportunity or pain point came straight from the LLM's
own free-text output field (`llmMatch?.evidence_id`, `p.evidence_id`) —
never generated or cross-checked by code, even for opportunities/pain
points that already had a real, independently quote-verified `evidence`
string sitting right next to it. The LLM's own field was essentially
always empty in practice; the actual evidence existed, it just wasn't
being surfaced as a stable, checkable id.

## What changed

`lib/pipeline/normalize.ts`:

- New `stableEvidenceId(prefix, text)` — a short deterministic hash
  (no new dependency), generating a real id FROM the evidence content
  itself rather than trusting an LLM-supplied field. Same
  "deterministic-over-LLM-trusted" discipline as the rest of this file's
  evidence-grounding work.
- **Pain points**: an `observed` claim that already passed
  `isQuoteGrounded()` now gets `evidence_id: stableEvidenceId('pp', evidence)`.
  `inferred` claims stay honest — no id is manufactured for reasoning that
  has no verified quote (Master Plan Rule 3: downgrade/reject unsupported
  claims, don't dress them as evidence-backed).
- **Opportunities, deterministic path (Path A)**: `d.id` (a real, stable
  id already generated by `opportunity-engine.ts` from a regex-matched,
  code-verified service-evidence hit — the strongest-grounded evidence of
  any path) is now always used as the fallback `evidence_id`, not just
  when the LLM happened to also supply one.
- **Opportunities, `llm_verified` path (Path B1)**: the `evidence` field
  here has already passed `verifyQuoteInContent()` against real content —
  now gets a real `stableEvidenceId('opp', evidence)`. `llm_inferred`
  (Path B2, no verified quote by definition) is left unchanged — same
  honesty discipline as pain points.

`app/admin/intelligence-lab/ResearchCard.tsx` (Master Plan Step 4.5 / 10.4
— "never present inference as fact," concise evidence display): opportunities
already carried `evidence`/`claim_type`/`source` in the data reaching this
component, just never rendered. Added a compact "Confirmed evidence" /
"Reasonable inference" badge per opportunity (derived from `source`/
`claim_type`, zero new data plumbing) and the evidence quote itself,
shown as a short italic line under the description — matching the plan's
own "concise cards, not huge dumps" instruction.

## Not done (explicitly out of scope this phase)

- Pain points don't get the same evidence/confidence badge treatment in
  `ResearchCard.tsx` yet — `painPoints` is flattened to plain `string[]`
  well upstream of the rendering component (loses `claim_type`/`evidence`/
  `evidence_id` before it arrives), which is a larger, more invasive
  plumbing change than the opportunities fix (which only needed to read
  fields already present at the render site). Flagged as a real follow-up,
  not silently skipped.
- No new `Evidence`/`Signal`/`Opportunity` database tables or a dedicated
  evidence-inspection UI page — the existing admin Debug tab
  (`_service_evidence_debug`, built 2026-07-24 per CLAUDE.md) already
  covers deep inspection; this phase's UI work targeted the main
  SDR-facing report, per Step 4.5's "enough to inspect the source, not a
  document dump" framing.
- The separate `evidence: EvidenceItem[]` array (used for
  `detected_factors` signal derivation) was not linked to the new
  opportunity/pain-point `evidence_id`s — they're deliberately two
  different mechanisms serving different consumers (signal derivation vs.
  opportunity/pain-point grounding); unifying them wasn't necessary to
  close the confirmed gap and would have been a larger, riskier change.
